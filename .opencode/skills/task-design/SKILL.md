# PURPOSE

Преобразовать проанализированные и проверенные требования в структурированные, независимые и готовые к реализации задачи (Issues) для команды разработки в Jira.

# INPUTS

Для применения скилла task-design необходимы следующие входные данные:

1. Структурированный результат анализа требований (выход скилла requirement-review).
2. Название проекта (Project Key) в Jira, где должны быть созданы задачи.
3. Принятые в команде шаблоны для описания задач (Definition of Ready).
4. Технические спецификации (описания API), если они приложены к требованиям.

> **Ограничение:** Скилл работает только с теми требованиями, которые прошли проверку качества (Quality Gates). Если в требованиях остались незакрытые противоречия или критически важные пробелы, скилл не должен создавать задачи.

# CONTEXT MANAGEMENT

При работе с входными данными агент обязан соблюдать следующие правила:

1. Использовать только информацию из предоставленного артефакта анализа требований.
2. Не придумывать архитектурные решения или названия переменных, если они не указаны в спецификации.
3. Если требование слишком объемное для одной задачи, разбивать его на несколько, но не терять логическую связь (указывать зависимости).

# PROCEDURE

При выполнении скилла агент действует строго последовательно:

1. Разбить общий массив подтвержденных требований на логические блоки (эпики или отдельные задачи). Каждая задача должна представлять собой атомарную единицу работы (реализуемую за 1-3 дня).
2. **Формирование структуры задачи.** Для каждой выделенной задачи определить и заполнить следующие атрибуты:
   - **Issue Type:** (например, Task, Story или Bug).
   - **Summary (Заголовок):** краткое, емкое название (до 80 символов). Должно отражать суть.
   - **Description (Описание):** контекст. Рекомендуемый формат: "Как [роль], я хочу [действие], чтобы [ценность]". Обязательно ссылка на исходное требование.
   - **Acceptance Criteria (Критерии приемки):** четкий список условий. Рекомендуется использовать формат Given-When-Then (Дано-Когда-Тогда) или маркированный список для проверки всех веток логики (включая обработку ошибок).
3. Определить зависимости между задачами (если Задача Б не может быть выполнена без Задачи А, это нужно указать).
4. Сравнить сформированные задачи с уже существующими в Jira (концептуально, на основе переданных данных), чтобы избежать создания дублей.
5. Проверить каждую задачу на соответствие критериям готовности (DoR): понятна ли цель, есть ли критерии приемки, не требует ли задача дополнительных исследований.

# RULES

При проектировании задач агент обязан соблюдать следующие правила:

1. Не создавать задачи, которые не имеют основания в проанализированных требованиях.
2. Не объединять в одну задачу функциональность, которая может разрабатываться независимо (разные разработчики/сервисы).
3. Не оставлять задачи без критериев приемки.
4. Не придумывать технические детали реализации (фреймворки, базы данных), если они не указаны в требованиях.
5. Не создавать подзадачи (Sub-tasks), если в этом нет прямой необходимости, лучше сделать независимые задачи со связями.
6. Форматировать текстовые поля (Description, Acceptance Criteria) с использованием Markdown-разметки, чтобы они красиво отображались в Jira.

# OUTPUT

Результат работы скилла должен быть представлен в виде структурированного **JSON-массива**, пригодного для автоматической передачи в Jira API.

Для каждой задачи указаны:
1. **Title (Summary)** — заголовок.
2. **Issue Type** — тип задачи.
3. **Description** — описание (с Markdown-разметкой и ссылкой на требование).
4. **Acceptance Criteria** — критерии приемки (в виде чек-листа или Given-When-Then).
5. **Dependencies** — ID или название задач, от которых зависит текущая (если есть).
6. **Traceability** — ссылка на исходное требование (ID требования из Confluence).

**Формат вывода:** Строго валидный JSON (без приветствий и текста вокруг, только JSON-массив).

# COMPLETION CRITERIA

Скилл task-design считается успешно выполненным только при соблюдении следующих условий:

1. Все подтвержденные требования декомпозированы на задачи.
2. Каждая задача имеет понятное название и описание.
3. Для каждой задачи сформулированы четкие, проверяемые критерии приемки.
4. Задачи не дублируют друг друга.
5. Установлена связь между каждой задачей и исходным требованием.
6. Сформирован итоговый JSON-массив задач, готовый к импорту в Jira.
7. В результатах нет выдуманных (неподтвержденных) требований или технических деталей.
