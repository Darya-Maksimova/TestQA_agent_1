# PURPOSE

Выполнить систематический анализ требований перед их использованием для формирования задач разработки (Jira) и проектирования тестовой модели в TMS (Testomat). Скилл формирует проверенный Requirement Review Artifact для следующих этапов Workflow.

# INPUTS

Для применения скилла необходимы следующие входные данные:

1. Текст требований (извлеченный из указанной страницы Confluence).
2. Связанные с требованиями бизнес-правила (при наличии).
3. Критерии приемки (при наличии).

> **Ограничение:** Скилл не должен самостоятельно искать отсутствующие данные за пределами переданного контекста. Если информации не хватает, это фиксируется как «отсутствующая информация» в результатах работы.

# CONTEXT MANAGEMENT

При работе с входными данными агент обязан соблюдать следующие правила:

1. Использовать только данные, относящиеся к анализируемой функциональности.
2. Не использовать устаревшие версии требований, если доступна более актуальная версия.
3. Не использовать предыдущие выводы агента как Source of Truth, если их можно проверить по исходным требованиям.
4. При большом объеме документации анализировать только релевантные фрагменты.
5. Не загружать и не запрашивать самостоятельно данные из Jira или TMS (внешние Tools управляются Agent Instruction).
6. Если входного Context недостаточно, явно зафиксировать Missing Information.

# PROCEDURE

При выполнении скилла агент действует строго последовательно:

1. **Определение функциональности:** Определить общую функциональность и бизнес-задачу, которую решает система (Scope).
2. **Выделение сущностей:**
   1. функциональные требования;
   2. нефункциональные требования (производительность, безопасность, доступность), если они есть;
   3. бизнес-правила;
   4. ограничения;
   5. критерии приемки;
   6. зависимости в требованиях.
3. **Поиск проблем:**
   1. выявить неоднозначности (допускающие несколько интерпретаций);
   2. выявить противоречия (конфликты требований друг с другом);
   3. определить отсутствующую информацию (пробелы, блокирующие разработку или тестирование).
4. **Выделение правил валидации и значимых граничных условий:**
   - Найти все явно указанные лимиты (min/max количество, длина строки и т.д.).
   - Найти правила жизненного цикла сущностей (можно ли добавлять дубликаты, можно ли редактировать созданное, что происходит при повторном использовании).
   - Если лимиты или правила дубликатов НЕ указаны, зафиксировать это в `Missing Information`.
5. **Определение основных Positive Flows и Negative Flows**, которые прямо следуют из требований.
6. **Определение QA-рисков**, связанных с требованиями.
7. **Формирование Open Questions** для спорных и неполных требований.
8. **Формирование результата:** Сформировать структурированный Requirement Review Artifact. Выполнить самопроверку (Self-Refine) по Completion Criteria (максимум 2 цикла исправлений).

# RULES

При выполнении анализа агент обязан соблюдать следующие правила:

1. Не добавлять отсутствующие бизнес-правила от себя.
2. Не выдавать предположения за подтвержденные требования. Все логические выводы должны быть вынесены в Open Questions как "Assumption" (Допущение).
3. Не изменять исходный текст требований.
4. Не создавать задачи в Jira в рамках этого скилла.
5. Не создавать тестовые сценарии в TMS в рамках этого скилла.
6. Не выполнять действия, не относящиеся к анализу требований.
7. Не искать отсутствующие данные за пределами предоставленного контекста (фиксировать их как пробел).
8. Не разрешать бизнес-неоднозначности самостоятельно.
9. Если два авторитетных фрагмента противоречат друг другу, зафиксировать Conflict.
10. Каждый существенный вывод должен иметь связь с исходным требованием или source reference, если это возможно.
11. Risk или Recommendation не должны подменять исходное Requirement.

# REASONING PATTERN

1. **Self-Refine / Critic:** После формирования первого варианта Requirement Review агент обязан проверить его по Completion Criteria. Если обнаружены исправимые недостатки, уточнить Artifact и выполнить повторную проверку. Максимальное количество циклов исправления — 2 (чтобы избежать бесконечного самоуточнения).
2. **Branching / Tree:** Не применяется по умолчанию. Если требование допускает несколько существенно разных трактовок, агент не выбирает одну ветвь, а фиксирует Ambiguity и варианты трактовки в блоке Open Questions для эскалации.

# OUTPUT

Результат работы скилла (Requirement Review Artifact) должен быть представлен **СТРОГО в формате валидного JSON** (без текста вокруг).

Структура JSON должна содержать следующие ключи:

```json
{
  "status": "success",
  "artifact": {
    "scope": "Строка с описанием функциональности",
    "requirements": ["Список функциональных требований"],
    "non_functional_requirements": ["Список NFR (если есть)"],
    "business_rules": ["Список бизнес-правил"],
    "acceptance_criteria": ["Критерии приемки"],
    "validation_rules": ["Правила валидации, лимиты и ограничения"],
    "dependencies": ["Зависимости"],
    "ambiguities": ["Неоднозначности с указанием мест в тексте"],
    "missing_information": ["Отсутствующая информация (включая неуказанные лимиты/правила дублей)"],
    "conflicts": ["Найденные противоречия"],
    "positive_flows": ["Позитивные сценарии"],
    "negative_flows": ["Негативные сценарии"],
    "boundaries": ["Граничные условия (только явно указанные в требованиях)"],
    "risks": ["QA-риски"],
    "open_questions": ["Вопросы для эскалации (включая Assumptions)"],
    "source_references": ["Ссылки на источники (ID/пункты)"]
  }
}
