# PURPOSE

Выполнить систематический анализ требований перед их использованием для формирования задач разработки (Jira) и проектирования тестовой модели (Qase). Скилл формирует проверенный Requirement Review Artifact для следующих этапов Workflow.

# INPUTS

Для применения скилла необходимы следующие входные данные:

1. Текст требований (извлеченный из указанной страницы Confluence).
2. Связанные с требованиями бизнес-правила (при наличии).
3. Критерии приемки (при наличии).

> **Ограничение:** Скилл не должен самостоятельно искать отсутствующие данные за пределами переданного контекста. Если информации не хватает, это фиксируется как «отсутствующая информация» в результатах работы.

# CONTEXT MANAGEMENT

При работе с входными данными агент обязан соблюдать следующие правила:

1. Использовать только данные, относящиеся к анализируемой функциональности.
2. Не использовать устаревшие версии требований, если доступна более актуальная версия.
3. Не использовать предыдущие выводы агента как Source of Truth, если их можно проверить по исходным требованиям.
4. При большом объеме документации анализировать только релевантные фрагменты.
5. Не загружать и не запрашивать самостоятельно данные из Jira или Qase (внешние Tools управляются Agent Instruction).
6. Если входного Context недостаточно, явно зафиксировать Missing Information.

# PROCEDURE

При выполнении скилла агент действует строго последовательно:

1. **Определение функциональности:** определить общую функциональность и бизнес-задачу, которую решает система (Scope).
2. **Выделение сущностей:**
   1. функциональные требования;
   2. бизнес-правила;
   3. ограничения;
   4. критерии приемки;
   5. зависимости в требованиях.
3. **Поиск проблем:**
   1. выявить неоднозначности (допускающие несколько интерпретаций);
   2. выявить противоречия (конфликты требований друг с другом);
   3. определить отсутствующую информацию (пробелы, блокирующие разработку или тестирование).
4. **Выделение правил валидации и значимых граничных условий**, если они следуют из требований.
5. **Определение основных Positive Flows и Negative Flows**, которые прямо следут из требований.
6. **Определение QA-рисков**, связанных с требованиями.
7. **Формирование Open Questions** для спорных и неполных требований.
8. **Формирование результата:** сформировать структурированный Requirement Review Artifact для дальнейшего использования.

# RULES

При выполнении анализа агент обязан соблюдать следующие правила:

1. Не добавлять отсутствующие бизнес-правила от себя.
2. Не выдавать предположения за подтвержденные требования.
3. Не изменять исходный текст требований.
4. Не создавать задачи в Jira в рамках этого скилла.
5. Не создавать тестовые сценарии в Qase в рамках этого скилла.
6. Не выполнять действия, не относящиеся к анализу требований.
7. Не искать отсутствующие данные за пределами предоставленного контекста (фиксировать их как пробел).
8. Не разрешать бизнес-неоднозначности самостоятельно.
9. Если два авторитетных фрагмента противоречат друг другу, зафиксировать Conflict.
10. Каждый существенный вывод должен иметь связь с исходным требованием или source reference, если это возможно.
11. Risk или Recommendation не должны подменять исходное Requirement.

# REASONING PATTERN

1. **Self-Refine / Critic:** После формирования первого варианта Requirement Review агент обязан проверить его по Completion Criteria. Если обнаружены исправимые недостатки, уточнить Artifact и выполнить повторную проверку. Максимальное количество циклов исправления — 2 (чтобы избежать бесконечного самоуточнения).
2. **Branching / Tree:** Не применяется по умолчанию. Если требование допускает несколько существенно разных трактовок, агент не выбирает одну ветвь, а фиксирует Ambiguity и варианты трактовки в блоке Open Questions для эскалации.

# OUTPUT

Результат работы скилла (Requirement Review Artifact) должен быть структурирован и содержать следующие блоки:

1. **Scope** (определение функциональности).
2. **Requirements** (список выявленных функциональных требований с кратким описанием).
3. **Business Rules** (перечень бизнес-правил).
4. **Acceptance Criteria** (если были выделены).
5. **Validation Rules** (правила валидации и граничные условия, если следуют из требований).
6. **Dependencies** (зависимости в требованиях, связи между разными частями системы).
7. **Ambiguities** (найденные неоднозначности с указанием мест в тексте).
8. **Missing Information** (отсутствующая информация, список пробелов).
9. **Conflicts** (найденные противоречия с описанием конфликта).
10. **Positive Flows** (основные позитивные сценарии).
11. **Negative Flows** (основные негативные сценарии).
12. **Boundaries** (значимые граничные условия).
13. **Risks** (выявленные риски, потенциальные проблемы при реализации или тестировании).
14. **Open Questions** (вопросы для эскалации и уточнения).
15. **Source References** (ссылки на источники для существенных выводов).

**Формат вывода:** структурированный список или JSON, пригодный для автоматической обработки агентом.

# ARTIFACT CONTRACT

1. **Producer:** Skill requirement-review.
2. **Consumers:** Skill task-design и Skill test-design.
3. **Artifact:** Requirement Review.
4. **Validation:** Completion Criteria этого Skill.
5. **Error Handling:** Если обязательный вход отсутствует или критическая неоднозначность не позволяет сформировать надежный Artifact, вернуть невалидный/заблокированный результат с описанием причины, а не заполнять пробелы предположениями.

# COMPLETION CRITERIA

Скилл считается успешно выполненным только при соблюдении всех условий:

1. Все предоставленные релевантные требования проанализированы.
2. Явные Requirements, Business Rules и Acceptance Criteria выделены.
3. Неоднозначности и противоречия либо выявлены и описаны, либо явно указано, что они не обнаружены.
4. Отсутствующая информация зафиксирована в виде списка пробелов.
5. Validation Rules и значимые Boundaries отражены там, где они следуют из требований.
6. Positive Flows и Negative Flows определены в пределах доступных требований.
7. QA Risks и Open Questions зафиксированы.
8. В результатах анализа нет выдуманных (неподтвержденных) требований.
9. Существенные выводы имеют Source References, если source reference доступен.
10. Сформирован структурированный результат (в соответствии с разделом OUTPUT), готовый для передачи на следующий этап.
