# PURPOSE

Разработать комплексную тестовую модель для проверки описанного функционала на основе проанализированных требований и подготовить её к загрузке в TMS (Testomat).

# INPUTS

Для применения скилла test-design необходимы следующие входные данные:

1. Структурированный результат анализа требований (выход скилла requirement-review).
2. Результат разбора контракта или технические спецификации (описания API), если они приложены к требованиям.
3. Название проекта в TMS (Project Code), где должна быть создана тестовая модель.
4. Принятые в команде стандарты написания тест-кейсов.

> **Ограничение:** Скилл работает только с теми требованиями, которые прошли проверку качества (Quality Gates). Если в требованиях остались незакрытые противоречия или критически важные пробелы, скилл не должен создавать тест-кейсы.

# CONTEXT MANAGEMENT

При работе с входными данными агент обязан соблюдать следующие правила:

1. Использовать только данные, относящиеся к анализируемой функциональности.
2. Не придумывать технические детали реализации (URL, названия полей БД, токены), если они явно не указаны в спецификациях.
3. При наличии противоречий в требованиях (из артефакта requirement-review) — не создавать тесты, а вернуть ошибку.

# PROCEDURE

При выполнении скилла агент действует строго последовательно:

1. На основе функциональных требований выделить модули или эндпоинты, которые подлежат тестированию.
2. Определить применимые техники тест-дизайна (классы эквивалентности, граничные значения, попарное тестирование) для каждого модуля.
3. **Проектирование позитивных сценариев (Happy Path):** Разработать сценарии, проверяющие корректное выполнение бизнес-логики при передаче валидных входных данных.
4. **Проектирование негативных сценариев:**
   - неверные типы данных;
   - отсутствие обязательных полей;
   - невалидные значения и превышение лимитов;
   - проверка корректного возврата ошибок сервера/валидации (400, 401, 403, 404, 500);
   - базовые проверки на безопасность (например, SQL-инъекции или XSS), если применимо к функционалу;
   - проверка повторного использования или добавления уже существующих сущностей (если это запрещено бизнес-логикой).
5. **Проектирование граничных сценариев:** Разработать сценарии, проверяющие поведение системы на границах допустимых значений (min, max, min-1, max+1), **явно указанных в требованиях**.
6. **Risk-based сценарии:** Выделить сценарии, проверяющие наиболее критичные для бизнеса части функционала (например, процесс оплаты или авторизации).
7. Для каждого сценария сформировать структуру тест-кейса (с обязательным указанием TestSuite — набора/модуля).
8. Привязать каждый тест-кейс к соответствующему требованию (Traceability).

# RULES

При проектировании тестовой модели агент обязан соблюдать следующие правила:

1. Не создавать тест-кейсы для функционала, который не описан в требованиях.
2. Обязательно включать позитивные, негативные и граничные сценарии для каждого модуля.
3. Не оставлять тест-кейсы без ожидаемого результата (Expected Result должен быть измеримым и конкретным).
4. Не описывать в тест-кейсах несуществующие технические детали.
5. Не создавать тест-кейсы в TMS напрямую в рамках этого скилла (только формирование JSON).
6. Не дублировать тест-кейсы.
7. Каждый тест-кейс должен быть атомарным (проверять одну конкретную вещь).
8. **Строгая классификация границ:** Граничный сценарий (Boundary) — это ТОЛЬКО проверка числовых или количественных лимитов (min, max, min-1, max+1), явно указанных в требованиях.
9. **Запрет на выдумывание границ:** Если в требованиях не указано максимальное/минимальное значение, агент НЕ ДОЛЖЕН придумывать его от себя. Необходимо зафиксировать этот пробел и не создавать граничные тесты для этого параметра.
10. **Разделение создания и повторного использования:** Сценарии «создание сущности» и «повторное использование/добавление уже существующей сущности» — это разные тесты. Повторное добавление (например, дубликат товара в корзине) относится к бизнес-логике или негативным сценариям, но НЕ к граничным.

# OUTPUT

Результат работы скилла должен быть представлен в виде структурированного JSON-массива, пригодного для автоматической передачи в TMS API. Для каждого кейса указаны:

1. **Title** — название тест-кейса (краткое и понятное).
2. **Type** — тип (позитивный / негативный / граничный / risk-based).
3. **TestSuite** — название набора (suite/модуля), к которому относится тест-кейс (для группировки).
4. **Preconditions** — предусловия (что должно быть настроено до начала теста).
5. **Steps** — шаги выполнения (с указанием конкретного запроса или действия).
6. **Expected Result** — ожидаемый результат (включая ожидаемый ответ или ошибку).
7. **Traceability** — ссылка на исходное требование.

**Формат вывода:** Только валидный JSON (без текста вокруг).

# COMPLETION CRITERIA

Скилл test-design считается успешно выполненным только при соблюдении следующих условий:

1. Для всех подтвержденных требований разработаны тест-кейсы.
2. В тестовой модели присутствуют позитивные, негативные и граничные сценарии (при условии, что границы явно заданы в требованиях).
3. Каждый тест-кейс содержит TestSuite, шаги и ожидаемый результат.
4. Установлена связь (traceability) между тест-кейсами и исходными требованиями.
5. Тест-кейсы не дублируют друг друга.
6. Сформирован итоговый JSON-массив тест-кейсов, готовый к импорту в TMS.
7. В результатах нет выдуманных (неподтвержденных) требований или лимитов.
