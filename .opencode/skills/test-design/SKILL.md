# PURPOSEi

Разработать комплексную тестовую модель для проверки описанного функционала на основе проанализированных требований и подготовить её к загрузке в Qase.

# INPUTS

Для применения скилла test-design необходимы следующие входные данные:

1. Структурированный результат анализа требований (выход скилла requirement-review).
2. Результат разбора контракта или технические спецификации (описания API), если они приложены к требованиям.
3. Название проекта в Qase (Qase Project Code), где должна быть создана тестовая модель.
4. Принятые в команде стандарты написания тест-кейсов.

> **Ограничение:** Скилл работает только с теми требованиями, которые прошли проверку качества (Quality Gates). Если в требованиях остались незакрытые противоречия или критически важные пробелы, скилл не должен создавать тест-кейсы.

# PROCEDURE

При выполнении скилла агент действует строго последовательно:

1. На основе функциональных требований выделить модули или эндпоинты, которые подлежат тестированию.
2. Разработать сценарии, проверяющие корректное выполнение бизнес-логики при передаче валидных входных данных.
3. **Проектирование негативных сценариев:**
   - неверные типы данных;
   - отсутствие обязательных полей;
   - невалидные значения;
   - проверка корректного возврата ошибок сервера/валидации.
4. Разработать сценарии, проверяющие поведение системы на границах допустимых значений.
5. Для каждого сценария сформировать структуру тест-кейса (с обязательным указанием TestSuite — набора/модуля).
6. Привязать каждый тест-кейс к соответствующему требованию.

# RULES

При проектировании тестовой модели агент обязан соблюдать следующие правила:

1. Не создавать тест-кейсы для функционала, который не описан в требованиях.
2. Обязательно включать позитивные, негативные и граничные сценарии для каждого модуля.
3. Не оставлять тест-кейсы без ожидаемого результата.
4. Не описывать в тест-кейсах несуществующие технические детали.
5. Не создавать тест-кейсы в Qase напрямую в рамках этого скилла.
6. Не дублировать тест-кейсы.

# OUTPUT

Результат работы скилла должен быть представлен в виде структурированного списка тест-кейсов (или JSON-массива), где для каждого кейса указаны:

1. **Title** — название тест-кейса.
2. **Type** — тип (позитивный / негативный / граничный).
3. **TestSuite** — название набора (suite/модуля), к которому относится тест-кейс (для группировки в Qase).
4. **Preconditions** — предусловия (что должно быть настроено до начала теста).
5. **Steps** — шаги выполнения (с указанием конкретного запроса или действия).
6. **Expected Result** — ожидаемый результат (включая ожидаемый ответ или ошибку).
7. **Traceability** — ссылка на исходное требование.

**Формат вывода:** JSON, пригодный для автоматической передачи в Qase API.

# COMPLETION CRITERIA

Скилл test-design считается успешно выполненным только при соблюдении следующих условий:

1. Для всех подтвержденных требований разработаны тест-кейсы.
2. В тестовой модели присутствуют позитивные, негативные и граничные сценарии.
3. Каждый тест-кейс содержит TestSuite, шаги и ожидаемый результат.
4. Установлена связь (traceability) между тест-кейсами и исходными требованиями.
5. Тест-кейсы не дублируют друг друга.
6. Сформирован итоговый JSON-массив тест-кейсов, готовый к импорту в Qase.
